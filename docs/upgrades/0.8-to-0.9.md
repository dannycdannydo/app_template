# Upgrading the template from v0.8 to v0.9

This guide is for a clone created from `v0.8.0` that is adopting the `v0.9.0`
release (PostgreSQL Row-Level Security tenant-isolation backstop). It records
what changed, how to apply it, and the manual steps that cannot be automated.
See `TEMPLATE_V0_9_SCOPE.md` for the release contract, ADR-0022 and
`docs/rls-rollout.md` for the design and rollout, and the version convention in
`CONTRIBUTING.md` for how template releases are numbered.

`v0.9.0` is additive and non-breaking: no public API is broken, no existing
migration is rewritten, every service keeps its explicit `organisation_id`
predicate and `404` behaviour, and the application layer remains the first
enforcement layer. The release adds a database default-deny backstop beneath it
and requires separate, least-privilege database roles in production.

## What the release adds

- PostgreSQL Row-Level Security enabled and forced on every organisation-owned,
  operational and platform table, with default-deny policies whose `USING` and
  `WITH CHECK` match.
- Separate database roles: `app_owner` (schema/migrations only), `app_runtime`
  (API and workers; non-owner, non-superuser, no `BYPASSRLS`), `app_coordinator`
  (outbox coordinator and reconciliation; dispatch-state policies),
  `app_metrics` (a `NOLOGIN` `SECURITY DEFINER` aggregate role) and
  `app_operator` (the isolated, audited operational credential and the only
  application role with `BYPASSRLS`).
- Parameterised transaction-local context (`app.organisation_id`,
  `app.user_id`, `app.job_id`, `app.platform_admin`, `app.platform_service`,
  `app.invitation_provider_id`) that clears on commit/rollback and cannot leak
  through the connection pool.
- A startup/deployment gate (`app.db.role_checks`, `make verify-db-roles`) that
  refuses to start a misconfigured API, worker or coordinator.

## New dependencies

None. The release uses only the existing SQLAlchemy/Alembic and PostgreSQL
capabilities.

## Configuration changes

Set up to three additional database credentials in production:

```dotenv
# Schema owner: Alembic/DDL only, never the runtime path.
DATABASE_URL=postgresql+asyncpg://app_owner:...@host:5432/db

# Ordinary API and Dramatiq worker path. Required in production.
DATABASE_RUNTIME_URL=postgresql+asyncpg://app_runtime:...@host:5432/db

# Outbox coordinator, reliability-metrics refresh and reconcile_jobs CLI.
DATABASE_COORDINATOR_URL=postgresql+asyncpg://app_coordinator:...@host:5432/db

# Isolated, audited operational tooling (the one BYPASSRLS role).
DATABASE_OPERATOR_URL=postgresql+asyncpg://app_operator:...@host:5432/db
```

- Production refuses to start without `DATABASE_RUNTIME_URL`, so the owner
  credential cannot silently become the ordinary application path. The
  coordinator credential is required by the coordinator process and
  `reconcile_jobs`.
- Locally, an empty `DATABASE_RUNTIME_URL` falls back to `DATABASE_URL` (the
  local `app` role is a superuser, so no policy is enforced). This fallback is
  not available in production.
- The credentials must authenticate as distinct roles; `make verify-db-roles`
  (also run at every runtime process start) proves the separation. An
  environment that points two URLs at the same role is rejected.

## Migrations

Ten additive, reversible migrations ship with v0.9. Apply them with:

```bash
make migrate
# or, deliberately:
cd backend && uv run alembic upgrade head
```

| Revision | Purpose |
| --- | --- |
| `c1d2e3f4a5b6` | `records` prototype: `app_runtime` role, `app_current_tenant_id()` and prototype policies |
| `d2e3f4a5b6c7` | Group 0 production enablement: `records`, `record_revisions` |
| `e3f4a5b6c7d8` | Group 1: `files` |
| `f5a6b7c8d9e0` | Group 2: `notifications`, `notification_deliveries`, the `app_metrics` aggregate read |
| `b8c9d0e1f2a3` | Group 3: `ai_requests`, `ai_outputs`, `ai_attachment_references`, `ai_scratch_uploads` |
| `c9d0e1f2a3b4` | Group 4a: `organisation_features`, `organisation_ai_settings` |
| `d0e1f2a3b4c5` | Group 4b: `jobs`, `job_attempts`, the `app_coordinator` role and the denormalised `job_attempts.organisation_id` |
| `f1a2b3c4d5e6` | Group 5: `organisation_memberships`, `membership_roles`, `invitations` (pre-tenant user/invitee/webhook policies; `ix_invitations_lower_email`) |
| `a2b3c4d5e6f7` | Group 6: `audit_events`, `outbox_events`, `maintenance_runs`, `webhook_events` and the isolated `app_operator` credential |
| `b4c5d6e7f8a9` | Group 7: `platform_roles`, `platform_role_permissions`, `platform_memberships`, `bootstrap_states` |

Each group enables and forces RLS, grants its new tables/sequences to
`app_runtime`, and ships a reversible downgrade. Group 4b adds a non-null
`job_attempts.organisation_id` with a composite parent foreign key; the
**migration downgrade is destructive** (it drops that column) and is gated by
the destructive-migration review. A live policy rollback instead disables the
group's policies and **retains** the additive column — see `docs/rls-rollout.md`
§4 for the two scopes and the mixed-version/expand–contract order.

## Worker and deployment implications

- Deploy the context-propagating code **before** applying a group's enforcement
  migration (expand → drain → contract); a policy enabled while a context-free
  consumer still reads the group is an incident, not a supported mixed-version
  state.
- Workers bind `app.job_id` for a single-row bootstrap read of the durable
  `jobs` row, clear it, then bind the row's organisation. The coordinator and
  `reconcile_jobs` run on `app_coordinator`, not `app_runtime`.
- The API, worker and coordinator each run the role gate at startup and abort on
  a misconfigured credential. Keep all three processes on the same release.
- Take logical backups with `DATABASE_OPERATOR_URL` (the one `BYPASSRLS` role):
  a `pg_dump` run as a non-`BYPASSRLS` role silently omits every row an enabled
  policy hides. See `docs/backup-and-recovery.md`.
- Every privileged `app_operator` use is audited without row contents or
  secrets; the credential is never loaded by an HTTP process or worker.

## Security implications

- Application scoping, permissions and foreign-resource `404` stay first;
  RLS is a backstop and is never a substitute for them.
- There is no implicit or request-selectable universal bypass. Platform access
  uses a validated transaction-local platform context; the only general
  cross-tenant read is the isolated, audited `app_operator` credential.
- Missing, empty or malformed context fails closed; a `NULL` tenant key is never
  read as "all rows".
- Runtime roles own no protected table, lack `SUPERUSER`/`BYPASSRLS` and cannot
  `SET ROLE` the operator credential; the startup gate enforces this.

## Manual adoption steps

1. Pull the `v0.9.0` release (or merge the release branch) and run
   `cd backend && uv sync` and `cd ../frontend && pnpm install`.
2. Provision the `app_owner`, `app_runtime`, `app_coordinator` and `app_operator`
   roles (the migrations create them `NOLOGIN` or safely adopt pre-existing
   ones; grant login passwords out of band and keep them out of the repo).
3. Set `DATABASE_RUNTIME_URL`, `DATABASE_COORDINATOR_URL` and
   `DATABASE_OPERATOR_URL` from `.env.production.example`.
4. Apply the migrations (`make migrate`).
5. Run `make verify-db-roles` and confirm each credential authenticates as a
   distinct, restricted role before serving traffic.
6. Rebuild and restart the API, worker and coordinator so all three run `v0.9.0`
   (the role gate aborts a misconfigured process).
7. Verify `/ready`, that `alembic current` matches the head revision, and that
   the protected tables report `relrowsecurity` **and** `relforcerowsecurity`.
8. Confirm the operator backup path: take a `pg_dump -Fc` with
   `DATABASE_OPERATOR_URL` and restore into an empty database during a drill.
9. Run `make check` and the real-PostgreSQL RLS suites listed in
   `TEMPLATE_V0_9_SCOPE.md` §4.
